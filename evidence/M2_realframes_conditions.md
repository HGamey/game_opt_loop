# M2 真机参考帧演化 — 测试条件与读数须知

配套产物：`M2_realframes_report.json`（验收报告）、`M2_realframes_frameset.json`
（参考帧集清单）、`../runs/evo_realframes_20260923/`（档案与逐代记录）。

日期 2026-09-23，设备 NX809J（91253241019A）。

---

## 1. 这一轮回答的问题

画质补测原先对着 headless runner 内置的**程序化图案**量 PSNR。本轮把真值换成
**真机原神截帧**，验证整条链路成立，并量出换尺子之后数字差多少。

## 2. 测试条件（读任何数字之前先看这一段）

| 项 | 取值 | 说明 |
|---|---|---|
| 载体 | `refbench`，每臂 400 帧，intensity 5 | 帧时与瓦数是场景内的真实值 |
| 冷机门槛 | **42 °C**（冻结协议写的是 32 °C） | 见下方「协议放宽」 |
| 主动散热 | **风扇开**，全程未变 | 两臂同风扇状态 |
| 供电 | **插着 USB 充电** | 见下方「功耗不作判据」 |
| 变异来源 | `--no-llm`，本地确定性变异器 | 固定种子 20260921，可逐字节复现 |
| 画质真值 | 19 张真机截帧，2688x1216 中心裁剪到 1920x1080 | 清单见 `M2_realframes_frameset.json` |
| A/B | 4 轮交替，Welch t 检验，p < 0.01 | 冻结协议其余部分未动 |

### 协议放宽：冷机 32 → 42 °C

冻结协议的 32 °C **假定挂了外置强吹风扇**。本机开着内置主动散热、屏幕亮着，
空载稳定在 41.5 °C，32 °C 等不到，只会耗尽等冷超时。42 °C 是实测空载地板上留一点余量。

这是在**放宽冻结判据**，必须写明。同类先例：M1（`M1_report.json`）用的是 40 °C。
放宽的是「什么时候允许开跑」，不是判定阈值；A/B/A/B 交替仍然在对付热漂移。

### 功耗不作判据，仅作记录

设备全程插着 USB 充电，量到的是 USB 输入轨，其中相当一部分是给电池充电、且随电量漂移。
**这条轨上的跨候选功耗比较不可信**，所以本轮的结论只建立在耗时/帧时与画质上。

这不是一句免责声明就算数的，实测也确实如此——5 个候选的功耗：

| 候选 | 功耗 (W) |
|---|---|
| gen0_baseline | 7.2034 |
| gen1_loc1 | 7.1995 |
| gen1_loc3 | 7.2027 |
| gen2_loc2 | 7.2039 |
| gen2_loc3 | 7.2034 |

极差 **4 mW**，低于支配比较的 `EPS_POWER`。把功耗这一维从支配排序里拿掉重算，
前沿**逐字不变**（`[gen0_baseline, gen1_loc3]`）。也就是说：本轮的前沿不依赖功耗，
把它当成「量了但没参与判定」来读是准确的，不是事后找补。

> 代码层面功耗目前仍是 Pareto 的第三维（`src/engine/pareto.rs`）。本轮它没起作用，
> 但在一台不充电的设备上它会重新起作用，而那时这条轨是否可信要另行确认。
> 契约层面把「这项功耗可不可比」显式化，应当与 smartperf 那条线一起做，不宜在此并行改。

## 3. 结果

### 3.1 换了参考图，同一个算子差多少

同一个算子 `gen1_llm1`，同一台设备，只换画质真值（headless 载体，单帧）：

| 参考图 | 基线臂 PSNR | 候选臂 PSNR |
|---|---|---|
| runner 内置程序化图案 | 38.666 dB | 42.826 dB |
| 真机截帧 `ref_00.png` | 29.674 dB | 30.168 dB |

差约 **9~12 dB**。真实画面的高频细节远多于合成图案，所以绝对 dB 低得多——
**绝对 dB 不可跨参考图比较**，这也正是报告里必须带 `quality_reference` 的原因。

### 3.2 一张不够：帧集内部的离散

赛道基线模板在 19 张真机帧上的逐帧 PSNR，均值 **34.521 dB**，
但单帧跨度是 **29.67 ~ 35.68 dB**，极差近 **6 dB**。

只取第一张（`ref_00.png`，29.67 dB）会比帧集均值低 4.9 dB。单张真机截帧的 PSNR
强烈依赖那一帧拍到了什么——对着天空几乎没有高频，对着灌木高频拉满。
一组覆盖不同内容的帧取平均，量的才是算子本身。

### 3.3 闭环结果

2 代 × 3 候选，6 个候选：4 个实测、2 个指纹去重、0 个门禁打回、0 个评测出错。
**4 份报告全部用真机参考帧**（`real_frame_reports: 4 / procedural: 0`）。

| 候选 | 耗时 (ms) | 画质 (dB) | p 值 | 裁决 |
|---|---|---|---|---|
| gen0_baseline | 0.264 | 34.521 | 1.16e-3 | PASS |
| gen1_loc1 | 0.530 | 37.796 | 3.02e-5 | PASS |
| gen1_loc3 | 0.479 | 37.796 | 2.51e-4 | PASS |
| gen2_loc2 | 0.826 | 37.796 | 1.41e-4 | PASS |
| gen2_loc3 | 0.536 | 36.091 | 4.56e-6 | PASS |

Pareto 前沿 2 条：`gen0_baseline`（0.264 ms / 34.521 dB）与
`gen1_loc3`（0.479 ms / 37.796 dB）。

**这一条是关键**：前沿不再塌回赛道基线模板自己。DESIGN §6.6 记录的失效模式是
——画质量不到时三目标塌成两目标，「什么都不做」在时延与功耗上永远最优，
LLM 候选一个都进不了前沿。现在画质这一维有真实读数了，一个真花了 0.22 ms
换来 3.3 dB 的算子能够凭画质站进前沿。

### 3.4 画质地板

接收端按 SPEC §4.1 把地板换成**本场基线臂实测值**（日志：
`画质地板改用本场基线实测 29.674 dB，契约携带的 38.666 dB 来自另一张参考图，仅作兜底`）。

上游 `is_admissible` 原本还在用赛道常数 38.666 dB（程序化图案上量的），
拿它去卡真机截帧上的 34.5 dB 会把**每一个**候选判成画质不合格——前沿清空、
亲本池清空、演化退化成反复生成基线。该问题已在本轮之前修掉（同一 PR），
否则这一轮会得到一张空前沿。

## 4. 不能从这份证据得出的结论

- **不能**说这些算子「省电」：功耗是充电态 USB 轨，仅作记录。
- **不能**把这里的 dB 和 `M1_report.json`（程序化图案）的 dB 放在一起比——两把尺子。
- **不能**把这里的帧时/瓦数和 M1 比——M1 是风扇关，本轮风扇开。
- 4 轮 × 2 臂、每臂 400 帧的样本仍然偏薄，p 值说明「差异真实」，不说明幅度稳定。
